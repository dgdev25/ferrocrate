# S180 — `docker compose wait` fails when the waited container has already exited

- suite: compose-e2e · class: product defect · status: closed 2026-08-30 — not a divergence: Docker Compose v5.4.0 reproduces the same failure for an already-exited service (verified 2026-08-29, engine-compat2 stream), so the ticket's claimed Docker baseline was wrong; no Ferrocrate defect exists to fix · first seen: 2026-08-28
- command: `docker compose wait faster` / `wait --down-project` where the service command is `sleep 2` and has already exited (TestWaitOnFaster, TestWaitAndDrop)
- Docker: `wait` returns immediately with the container's exit code (0 for a clean exit) and, with `--down-project`, removes the project's containers.
- Ferrocrate: exit 1; the failing step reports `no containers for project "e2e-wait-and-drop"` even though `ps` lists the project's containers (including the exited one).
- impact: 2 failures.
- regression tests: `run -d` a container that exits, `compose wait <service>` asserting exit 0 and the exit code; `wait --down-project` asserting all project containers are removed.
- verification note: left open. Docker Engine 29.7.2 with Docker Compose v5.4.0 reproduced the same `no containers for project` result for an already-exited service, so the ticket's claimed Docker baseline could not be confirmed in this environment and no unverified divergence was changed.
