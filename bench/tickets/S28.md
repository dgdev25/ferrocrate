# S28 — run -d writes progress and a decorated line to stdout instead of the bare container id
- found by: the differential fuzzer, 22 sequences, every one diverging at the first step · class: product · status: closed · first seen: 2026-08-27
- command: `ferro-cli run -d --name x alpine:3.20 sleep 5`
- Docker stdout: `3e2bb51c8e916f6d3375bab077df8a9de79ca85d55b7835e7f5caabb85a5dd32` and nothing else. Pull progress goes to stderr.
- Ferrocrate stdout:
  ```
  pull: fetching image=registry-1.docker.io/library/alpine:3.20
  pull: image=registry-1.docker.io/library/alpine:3.20
  run: container_id=045d1a18723d9f821157fcddcb4b0418 pid=3011977 network_backend=ebpf
  ```
- impact: `CID=$(docker run -d ...)` is the most common scripted use of the command and it captures three lines of diagnostics instead of an id. Every script, CI job and tool that reads the id back is broken. The same shape affects any command whose stdout is a value rather than a report.
- fix: send progress and diagnostics to stderr; write only the container id to stdout, with no prefix. Audit the other value-returning commands for the same shape: `create`, `build -q`, `commit`, `volume create`, `network create`.
- test: assert `run -d` stdout is exactly one line matching a 64 or 12 character hex id, and that pull progress appears on stderr instead.
- note: the bench did not catch this because its run-detached step only checks the exit code. The fuzzer compares normalised stdout between engines, which is precisely the class of defect it exists to find.

## Verification
Verified 2026-08-27. Both print sites now emit the bare id with diagnostics on stderr, and `CID=$(ferro-cli run -d ...)` followed by `rm -f "$CID"` succeeds. Regression test `run_detached_stdout_is_only_the_container_id` asserts the captured value addresses the container. The id's own shape is wrong on both paths and is filed separately as S61.
