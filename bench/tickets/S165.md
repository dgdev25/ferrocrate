# S165 — Docker CLI attached-run protocol is incomplete on the compatibility socket
- suite: cli-e2e (`TestRunAttach/*`, `TestRunReadAfterContainerExit`) · class: product · status: open (partial fix 4b2e24e5) · first seen: 2026-08-28
- command: run `docker run -a stdin|stdout|stderr --rm alpine sh -c 'sleep 1 && exit 7'` from a PTY, and run the upstream 18,933,764-byte `docker run --rm -i alpine sh -c 'cat -'` read-after-exit case through the Ferrocrate socket.
- Docker: each selected attached stream returns the process exit status 7, and the large stdin/stdout transfer completes after the container exits without losing bytes.
- Ferrocrate: all three `TestRunAttach` children exit 1 rather than 7; `TestRunReadAfterContainerExit` reports `unable to upgrade to tcp, received 404` and reads 0 of 18,933,764 bytes. The parent `TestRunAttach` is the aggregate of those three child failures.
- cause: the Docker-compatible attached-run path does not provide the full CLI-required TCP upgrade/hijack and stream lifecycle for these non-TTY selected-stream variants. Existing direct attach tests cover other handshake variants but not this CLI execution path.
- scope: `docker run -a`, piped stdin/stdout, post-exit draining, and any client relying on Docker's attach transport rather than a local native CLI stream.
- test: run the upstream four CLI e2e cases against an isolated socket; assert status 7 for each selected stream and byte-for-byte completion of the 18,933,764-byte post-exit transfer, including the successful TCP upgrade.
- evidence: 2026-08-28 isolated `SUITE_SRC=/data/dev/bench-suites bash bench/suites/run-suite.sh cli-e2e --engine ferrocrate` at `d3122b16`; all four have passing Docker oracle records.

## Fix

The daemon now releases its container-store request guard while `/containers/{id}/start` waits for the already-sent attach upgrade to publish its `101 Switching Protocols` response, then reacquires it for the lifecycle transaction. This removes the circular queue in Docker's create/attach/start sequence: start could previously wait for attach readiness while attach itself waited for the guard start held.

## Verification

Focused Docker-compat integration tests passed on 2026-08-28: `docker_compat_pre_start_hijack_does_not_block_start_on_the_store_queue` races the upgraded attach request with `/start`, and `docker_compat_post_start_hijack_upgrades_before_log_files_exist` confirms the TCP upgrade remains available immediately after start. The upstream `TestRunAttach` children also pass against the rebuilt isolated daemon. `TestRunReadAfterContainerExit` remains open: after the binary-safe log readback change it still resets the TCP connection after 1,059 of 18,933,764 bytes, so a second input/output backpressure or lifecycle defect remains.

Reproduction against the rebuilt current daemon on 2026-08-28 still failed
`TestRunReadAfterContainerExit` with a reset connection. The persisted stdout
contained the first 1,059-byte random-data line while the `cat -` workload was
still alive. A nonblocking FIFO-write experiment was reverted after it failed
the same focused test earlier with zero output; the remaining defect is not
the already-fixed socket output queue or binary log readback.
