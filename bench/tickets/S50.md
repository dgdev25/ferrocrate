# S50 — image: `image prune` removes the image a running container is using
- apps: all · step: image-prune · class: product · status: closed (b1586b30) · first seen: 2026-08-27
- command: `image prune -f` while a container started from the image is running (minimal sequence: `run -d --name fz-<tag> alpine:3.20 sleep 300`, `image prune -f`)
- Docker: `docker image prune` never removes an image any container references, running or stopped; output `Total reclaimed space: 0B` and the container keeps running.
- Ferrocrate: `image prune: removed=1`; the base image is gone from `images` while the container still runs.
- cause: `handle_image_prune` listed every stored reference and pruned it without consulting container state.
- scope: any prune between `run` and `rm` destroys the container's root filesystem source; this is the only ticket here that can lose real data.
- test: start a container from the base image, run `image prune -f`, assert the image is still listed and the container still runs.
- seed: `bench/fuzz/seeds/20260827-image-prune-*.json`

## Fix
`handle_image_prune` takes the set of image references the container store holds and skips every record in it. `docker_image_container_references` collects the keys (repository form and `repository@digest` form, registry host stripped, so a container started from `alpine:3.20` protects the digest-form reference ferro records). The guard runs in the direct CLI path, in `system prune`, and in the daemon's `POST /images/prune` route.

## Verification
Verified 2026-08-27 in the isolated fuzz runtime: `run -d` + `image prune -f` while running gives `removed=0`, the base image stays in `images`, and the container keeps running; after `rm` the same prune removes the image. Workspace tests pass, `verify-no-warnings.sh` passes, conformance 85/85 in both DOCKER_BUILDKIT modes.
