# S52 — image: `load` rejects a tarball produced by `docker save`
- apps: all · step: image-load · class: product · status: closed (2450ac46) · first seen: 2026-08-27
- command: `docker save alpine:3.20 -o img.tar`, then `ferro-cli load -i img.tar`
- Docker: `docker load` accepts it — a docker-save tarball is the portable image format; loading it on another host is its purpose.
- Ferrocrate: exit 1, `docker: image load config digest does not match its filename`. The loader validates a naming convention its own `save` produces and rejects docker's manifest/layout for the same image content.
- cause: the load path expects the ferro save layout (config file named by its digest) instead of parsing the OCI/docker archive manifest. Docker names config blobs by digest in its layout too, so the mismatch is in how the digest-to-filename expectation is computed.
- scope: image transfer between docker and ferrocrate hosts, backup/restore workflows, the airgapped install path. Found by inspection while reseeding the isolated store after S50 emptied it.
- test: `docker save alpine:3.20` to a tarball, `ferro-cli load -i` it, assert exit 0 and that `images` lists alpine:3.20; run a container from it.
- note: blocked verification of `save`/`load` round-trips across engines; the fuzzer's save/load steps only round-trip within one engine and pass.
