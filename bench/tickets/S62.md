# S62 — the archive endpoint answers 404 for a container id that inspect resolves
- suite: buildkit-dockerfile (the suite could not start at all) · class: product · status: resolved · first seen: 2026-08-27
- reproduce, against the Docker-compat socket:
  ```
  id=$(curl -s --unix-socket $SOCK -X POST -H 'Content-Type: application/json' \
       -d '{"Image":"registry:2"}' http://localhost/v1.45/containers/create | jq -r .Id)
  curl -o /dev/null -w '%{http_code}\n' --unix-socket $SOCK http://localhost/v1.45/containers/$id/json
  curl -o /dev/null -w '%{http_code}\n' --unix-socket $SOCK "http://localhost/v1.45/containers/$id/archive?path=/bin/registry"
  ```
- Docker: both return 200. Ferrocrate: inspect returns 200, archive returns 404 for the same id, on both HEAD and GET.
- consequence: `docker cp` out of a created-but-never-started container fails. That is the standard way to extract a binary from an image, and it is how the BuildKit suite obtains its test registry, so the suite could not run at all.
- likely cause: the archive handler resolves containers through a different lookup than inspect, one that only sees started or running containers.
- fix: resolve the id through the same lookup every endpoint uses, and support a created container that has never run.
- test: create a container without starting it, then GET its archive for a path from the image, and assert 200 with a tar stream.
- resolution: `7512f3a7` routes archive lookup through the common pending-container resolver and materializes an image rootfs without launching a workload. Its Docker socket regression creates an image-backed container, never starts it, and verifies a 200 tar stream for `/bin/busybox`.
