# S51 — run: `kill`, `top` and `exec` succeed on stopped containers
- apps: all · step: kill, top, exec · class: product · status: closed (849e56cd) · first seen: 2026-08-27
- command: `kill <name>` on a stopped container (minimal sequence: `run -d --name fz-<tag> alpine:3.20 sleep 300`, `kill fz-<tag>`, `kill fz-<tag>`); same shape for `top` and `exec`
- Docker: exit 1 — `cannot kill container: ... is not running` / `container ... is not running`. Both verbs require a running container.
- Ferrocrate: `kill` exit 0 with an id line (kills an already-dead container as if it succeeded); `top` exit 0, printing a table whose STATE column says `unknown`; `exec` exit 0, running the command in the stopped container and printing its output.
- cause: the kill, top and exec paths do not validate that the container is running before acting.
- scope: scripts that kill and check the exit status cannot distinguish "it was running and I killed it" from "it was already dead" — the one signal docker gives for double-kill races. `exec` on a stopped container is confirmed affected (found by the fuzzer, not just inspection).
- test: run detached, stop, then `kill`; assert exit 1 and an error naming the container. Same for `top` and `exec`. Assert `kill` on a running container still exits 0.
