# S168 — run: `rm -f` on a renamed container's old name fails instead of being a no-op

- apps: all · step: rm-force · class: product · status: open · first seen: 2026-08-28
- command: `run -d --name fz-<tag> alpine:3.20 sleep 300`, `rename fz-<tag> fz-<tag>-r`, then `rm -f fz-<tag>` (the old, now-unused name)
- Docker: exit 0 — after a rename, the old name no longer resolves to anything, so `rm -f` on it is the documented no-op-on-missing behavior (the same contract S46 already fixed for a name that was never used).
- Ferrocrate: exit 1. The old name apparently still resolves to something (or the lookup path differs from S46's fix), so the forced removal doesn't take the no-op path.
- cause: unclear from the fuzzer evidence alone — needs investigation into whether the old name still has a live container-store entry after rename, or whether `rm -f`'s name resolution and S46's no-op path diverge for a renamed (vs. never-existed) name.
- scope: any script that renames a container and later tries to force-remove it by the old name, expecting Docker's no-op contract.
- test: create a container, rename it, `rm -f` the old name, assert exit 0 with no output, matching S46's existing no-op-on-missing coverage.
- evidence: found by the 200-sequence differential fuzzer during the S40-S53 acceptance run, 2026-08-28, verified against Docker directly. 26 of 85 fuzzer divergences in this run were this exact class.
