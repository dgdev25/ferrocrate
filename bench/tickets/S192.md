# S192 — rootless lifecycle signalled only the bubblewrap launcher, orphaning the workload

- apps: rootless containers whose bubblewrap launcher retains a child workload (found with Battleships on host networking) · steps: pause, unpause, stop, kill, restart, rm, daemon reconciliation · class: product · status: closed · first seen: 2026-08-28
- command: build Battleships, then `ferro-cli run -d --name s192-battleships --network host -e PORT=3212 -v s192-battleships-data:/app/data s192-battleships:latest`; exercise pause/unpause/stop/restart/rm while probing HTTP and the host process group.
- Docker: lifecycle operations control the complete container-owned process unit. Pause blocks service progress; stop/kill/rm leave no workload; restart creates one replacement; volumes persist.
- Ferrocrate before: the durable PID named the bwrap launcher, while lifecycle paths variously froze/signalled that PID or a direct child. Killing the launcher allowed its Node child to reparent to the host supervisor, retain port 3212, and collide with the replacement (`Database already open`).
- cause: non-TTY launches already created a private process group, but lifecycle code did not use that ownership boundary consistently. Late descendant walks lost children as soon as an intermediate process exited and reparented them.
- fix: introduce verified group signalling bound to the recorded leader PID, kernel start time, same-numbered leader-owned PGID, and caller UID. Pause/resume target the verified group; graceful stop signals the group and snapshots member identities for safe escalation after reparenting; SIGKILL, restart, forced removal, and orphan cleanup use the same process-unit semantics. Direct-PID fallback preserves legacy/rootful records only after start-time verification.
- automated proof: `ferro-core/tests/process_tree_lifecycle.rs` deterministically spawns a process-group leader plus child and covers pause/resume progress, stop collection, no orphan progress, and mismatched-start-time refusal. Both stop tests were observed failing before production edits and passing afterward.
- real proof: release binary from this clone, isolated `FERROCRATE_HOME`, Battleships host network on port 3212. Pause caused a one-second HTTP timeout and unpause restored HTTP; stop freed port 3212 and left zero live PGID members; restart changed the leader PID, produced exactly one Node workload, returned HTTP 200, and preserved a byte-identical `/api/memory/export` from the named volume; `rm -f` again left zero live members and retained the volume.
