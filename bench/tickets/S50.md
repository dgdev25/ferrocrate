# S50 — image: `image prune` removes the image a running container is using
- apps: all · step: image-prune · class: product · status: open · first seen: 2026-08-27
- command: `image-prune --force` while a container runs from the image (minimal sequence: `run -d --name fz-<tag> alpine:3.20 sleep 300`, `commit fz-<tag> fzimg-<tag>:latest`, `image prune -f`)
- Docker: never removes an image that any container — running or stopped — references. The running container keeps its rootfs.
- Ferrocrate: the prune removed both the committed image and the base `alpine:3.20` while `fz-<tag>` was still running from it (`removed=2`, `images` empty). The next `run` of the same image must re-pull from the registry; under Docker Hub's pull rate limit this turns into an outage.
- cause: the prune path counts an image as unused without checking container references.
- scope: severity high — a prune during any workload evicts the images underneath it. Combined with S49 (tagged images pruned), a single `image-prune --force` empties the store.
- test: run a detached container, `image prune --force`, assert the base image is still listed and the container still runs.
- seed: `bench/fuzz/seeds/20260827-image-prune-*.json`
- note: the fuzzer now re-pulls the base image in its cleanup (ensure_base_image) so this behaviour does not cascade into rate-limited false divergences; that is a bench workaround, not a fix.
