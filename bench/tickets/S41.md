# S41 — run: container state is reported as `killed` after a kill
- apps: all · step: kill · class: product · status: open · first seen: 2026-08-27
- command: `kill <name>` on a running container, then `ps -a` (minimal sequence: `run -d --name fz-<tag> alpine:3.20 sleep 300`, `kill fz-<tag>`, `ps -a`)
- Docker: the container's State is `exited`. Docker's state vocabulary is created, running, paused, restarting, removing, exited, dead — `kill` is a way to reach `exited`, not a state of its own.
- Ferrocrate: the container's status is `killed`. Anything that parses `docker ps` output for `exited` (compose, watchtower-style restart loops, the bench suites' wait-for-exit helpers) never matches.
- cause: the container status model stores the termination cause as the status instead of a terminal state.
- scope: `kill` and possibly an unclean shutdown path. `stop` reports `exited` correctly, so only the signal path is affected.
- test: run detached, `kill`, then assert `ps -a` reports `exited` (both text and `--format json`).
- seed: `bench/fuzz/seeds/20260827-kill-6d78b0a1.json`
- note: the fuzzer maps `killed` to `exited` when comparing state so sequences continue past a kill; the mapping is in `bench/fuzz/fuzz.py` (`FerroEngine.STATUS_MAP`) and must be removed when this is fixed.
