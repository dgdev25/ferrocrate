# S31 — daemon: HEAD /_ping returns 404, so every Docker-SDK client fails its handshake
- suite: buildkit-dockerfile (1076 of 1077 Ferrocrate-only failures behind it) · class: product · status: open · first seen: 2026-08-27
- command: `curl -I --unix-socket <sock> http://localhost/_ping` against the Docker-compat socket
- Docker: `HEAD /_ping` returns 200 with `Api-Version`, `Ostype`, `Builder-Version` headers; `GET /_ping` returns the same plus the body `OK`.
- Ferrocrate: `HEAD /_ping` returns `404 {"message":"not found"}`; only GET is routed. Verified with curl on 2026-08-27 against release-artifacts/ferro-cli.
- cause: the Docker Go client (`moby/moby/client` v0.5.1, used by buildkit, compose, testcontainers) starts every session with `Ping`, which sends HEAD and falls back to GET only when HEAD answers 405. With 404 the fallback does not trigger and the client reports "failed to connect to /_ping endpoint". BuildKit's sandbox startup (`workers/dockerd.go waitForAPI`) retries for 5 s and aborts, so no test reaches the Dockerfile frontend at all.
- scope: route HEAD alongside GET on `/_ping` (and `GET /_ping` should carry `Api-Version`, `Ostype`, `Builder-Version` headers the way Docker does — today it returns none, which makes SDK clients negotiate down to the oldest API version). Any 405-vs-404 policy for unknown methods on other routes deserves the same review.
- test: `curl -I --unix-socket <sock> http://localhost/_ping` returns 200; a Go client with `client.NewClientWithOpts(WithHost(...))` completes `Ping()` without error.
- workaround: bench/suites/run-suite.sh's gate answers HEAD /_ping itself so the suite can still produce numbers; the workaround does not close this ticket.
