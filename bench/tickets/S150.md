# S150 — daemon: `GET /plugins` returns 404 instead of an empty Docker plugin collection
- suite: moby-integration (117 directly recorded product failures; four aggregate parent failures and one merged parallel record have the same setup cause) · class: product · status: resolved · first seen: 2026-08-27
- command: `GET /v1.45/plugins` through the Docker-compatible socket on a daemon with no installed plugins.
- Docker: answers `200 OK` with the JSON collection `[]`. Moby calls this from `environment.ProtectAll` before each integration test to preserve pre-existing plugins.
- Ferrocrate: answered `404 {"message":"docker: plugin listing is unsupported; plugins are installed from signed local manifests"}`. The Moby client treats this as an ordinary error (not `NotImplemented`), so setup aborts before the test body for container, image, network, volume, build, and daemon cases.
- cause: the compatibility route treated plugin listing as part of unsupported plugin lifecycle management, even though listing an empty locally-installed set needs no remote plugin implementation.
- scope: preserve the explicit 404 boundaries for plugin pull/install/enable/disable/remove, but make `GET /plugins` return an empty JSON collection until local-manifest enumeration is exposed.
- test: `plugin_list_returns_an_empty_docker_compatible_collection` starts the socket daemon and asserts `GET /plugins` returns HTTP 200 and a JSON empty array; `plugin_management_family_reports_explicit_boundaries` retains coverage that mutating plugin routes are 404.
- resolution: `GET /plugins` now returns `200 []`, allowing Docker/Moby setup to proceed without falsely advertising plugin lifecycle support.
