# S193 — rootless Compose project networking died with its first service

- apps: rootless Compose projects with an implicit or named bridge network · class: product · status: open · first seen: 2026-08-28
- symptom: Compose used its first running application container as the rootless slirp4netns namespace leader. A short-lived migration or setup service could exit before followers joined, leaving them unable to start or leaving their published ports unreachable.
- cause: the namespace and slirp helper had no project-owned lifecycle. The leader map was populated after a service launched, so it could not provide an atomic, durable ownership boundary for setup, cross-runtime reaping, forwarding, or teardown.
- fix in progress: create a locked, durable rootless network lease before services launch. The lease owns a dedicated user/network namespace coordinator and slirp helper, uses PID start-time plus generation CAS identity, records forwarding IDs transactionally, and is removed only after Compose-down removes every consumer.
- operational proof: `FERROCRATE_RUN_ROOTLESS_SHARED_COMPOSE_E2E=1 cargo test -p ferro-cli --test rootless_compose_integration rootless_compose_short_lived_first_service_keeps_named_network_and_ports_alive -- --nocapture`. The fixture makes the first named-network service exit immediately, verifies the follower shares its namespace and answers through two published ports, then verifies down removes both ports and the lease registry.
- additional operational proof: the same opt-in integration target exercises explicit `network_mode: bridge`, verifies its published port is reachable, and verifies `compose down` releases it. The named-network case covers two published ports. The full regression gate passed after the lease implementation (2,266 workspace tests; BuildKit and classic conformance 85/85 each).
- remaining before closure: focused failure-injection coverage and independent review.
