# S190 — cross-runtime slirp4netns ownership/reaping isolation
- app: rootless runtime · step: startup reconciliation / published port · class: product · status: closed
- observed: with two isolated `FERROCRATE_HOME` values for the same UID, runtime A could keep a rootless bridge container and published port running, then any `ContainerRuntime` initialization against runtime B scanned the shared `/tmp/ferrocrate-slirp-<uid>` directory, treated A's helper as absent from B's store, and killed it. A remained recorded `running` with a dead published port.
- cause: short slirp API socket paths encoded only the container ID beneath a per-UID global directory. The startup reaper consequently used directory membership as runtime ownership even though that directory was shared by every isolated store for the UID.
- fix: socket paths now include the durable `runtime-instance-id` as a short namespace component. Startup reaping considers only helpers in the current runtime's namespace, preserves helpers from other stores, and still reaps helpers absent from the current runtime's durable records. Legacy sockets directly under the old per-UID directory are ownership-ambiguous and are not guessed at; recorded legacy helpers remain stoppable/removable by their persisted PID and process-start-time identity.
- verification: deterministic red-green coverage uses two independent SQLite runtime stores and a live slirp-shaped helper; focused slirp tests also cover current-runtime orphan reaping, durable-record preservation, legacy ambiguity, terminal PID/start-time cleanup, disjoint namespaces, and the Unix socket length limit. A release CLI real-host probe started a BusyBox HTTP server in runtime A on rootless bridge port `18193`, confirmed the response, initialized runtime B with `containers`, then confirmed runtime A's slirp PID and published response remained live while runtime A still reported `running`; cleanup stopped and removed the container.
