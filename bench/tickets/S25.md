# S25 — build: Maven checkstyle fails under Ferrocrate but passes under Docker
- app: spring-petclinic · step: build · class: product · status: fixed and revalidated · first seen: 2026-08-27
- command: `ferro-cli build -t bench/spring-petclinic:latest .` on the app's own Dockerfile
- Docker: build passes. Ferrocrate: Maven fails with `checkstyle violations`, so the build exits non-zero and 32 later steps fail behind it.
- likely cause: the build context differs from Docker's. Candidates, in order: `.dockerignore` entries not applied the same way, so checkstyle scans files Docker excludes; `COPY . .` placing context contents differently after the run-4 change; file modes or line endings altered in transit.
- reproduce: build the app with both engines, then `docker run --rm <image> find /workspace -newer pom.xml` on each and compare the file lists. The first difference is the cause.
- note: the recorded stderr keeps only the last 400 bytes, which held Maven's epilogue rather than the violation names. Diagnosing this needs the build journal to retain the failing step's full output.
- cause and fix (2026-08-27): `COPY . .` under a `WORKDIR` copied the context directory as a nested directory instead of copying its contents. The corrected filtered context path preserves Docker's contents semantics and applies `.dockerignore` before source selection. Failed `RUN` output is now retained in full in the durable build journal rather than a bounded tail.
- proof: `copy_dot_into_workdir_copies_context_contents_not_context_directory` covers the workspace placement and ignored checkstyle input; `build_journal_retains_failure_output_larger_than_one_mebibyte` covers full diagnostics. After seeding the isolated store, the full Spring Petclinic bench completed under `with-host-lock.sh`; workspace tests, warning verification, and both 85/85 conformance modes also passed.
