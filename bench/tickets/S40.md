# S40 — run: `start` on a running container fails instead of being a no-op
- apps: all · step: start · class: product · status: open · first seen: 2026-08-27
- command: `docker start <name>` on a container that is already running (minimal sequence: `run -d --name fz-<tag> alpine:3.20 sleep 300`, then `start fz-<tag>`)
- Docker: exit 0, prints the container name, container keeps running. Starting a running container is a success.
- Ferrocrate: exit 1, `start: fz-<tag>: invalid container state: container is already running`.
- cause: the start path rejects any container whose current state is not a stopped state. Docker's contract: start on a running or paused container succeeds without doing anything (the daemon logs a warning at most).
- scope: the same guard likely rejects `start` on a `created` container or after `stop --timeout`; every script that unconditionally starts containers after a crash-restart breaks on the first already-running one.
- test: run a detached container, `start` it again, assert exit 0 and that `ps` still shows it running. Also assert `start` on a stopped container still works and on a `created` container starts it.
