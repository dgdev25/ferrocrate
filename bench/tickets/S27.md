# S27 — compose: every service is refused as an unauthorized child
- apps: all eleven with a compose file · step: compose-up · class: product · status: partial fix — downstream rootless-network and upstream-suite qualification pending · first seen: 2026-08-26, present in every run since
- command: `ferro-cli compose up -d --build`
- Docker: brings the stack up. Ferrocrate: `compose partial result: <service> run failed: runtime mutation mediation failed: compose execution request digest does not match authorized child`.
- cause: `ferro-core/src/runtime.rs` computes `run_execution_digest` from the pinned image, command, environment, labels, annotations, healthcheck, restart policy, limits, workdir, user, name, port mappings and the normalized request, then rejects the launch unless it equals the digest compose authorized through `fanout_request_digest_matches`. Compose authorized unresolved image defaults (`workdir: None`, `user: None`, and an incomplete command), while `handle_run` resolved the image command and the runtime later inherited `WorkingDir` and `User`. The check arrived with `d806d82b`.
- fix: Compose resolves the pinned image configuration once after image prerequisites and before child authorization. It binds command, workdir, user, and image-declared volume targets into `normalized_run_execution_digest`, then passes the same resolved command and pre-materialized anonymous-volume mounts to `handle_run`. The launcher consumes those exact mounts instead of creating image volumes after authorization. The comparison remains enforced; a changed command is still rejected.
- to find it: log both digests and their inputs at the point of comparison, then diff the input sets. The likely culprits are fields the runtime fills in after compose authorized the child: values inherited from the image config, a normalized network mode, or a generated container name.
- scale, measured 2026-08-27 with docker/compose's own e2e suite: 270 tests, Docker passes 264, Ferrocrate passes 22. That is 229 product failures against 6 that fail on both engines. The entire fourteen-application bench has 144. This single defect is the largest in the project.
- impact: compose-up fails on 11 of 14 applications, and compose-health, compose-ps and compose-down fail behind it. This is the largest remaining cluster in the bench.
- proof: `cargo test -p ferro-cli compose_resolves_image_command_workdir_and_user_before_authorization` passes with an image `Volumes` declaration; `cargo test -p ferro-core compose_run_executor_rejects_a_mismatched_normalized_digest` authorizes `true`, mutates it to `false`, and is rejected. The S27 fixture now declares `WORKDIR`, `USER`, and `VOLUME`; its build reaches launch without the compose digest rejection. Full two-service port proof remains blocked by the separate rootless networking failure (`run: publish requires --network bridge` after the service joins the leader namespace). Post-run check observed `bwrap=0`; the host already has two `slirp4netns` processes, so the required zero-process cleanup proof is not yet established.
- qualification blocker: on 2026-08-27, the required `SUITE_SRC=/data/dev/bench-suites bash bench/suites/run-suite.sh compose-e2e --engine ferrocrate` collected zero tests because `/data/dev/bench-suites/compose` has an inconsistent vendor tree. Direct `go test -mod=vendor` fails before test discovery with modules required by `go.mod` missing from `vendor/modules.txt`; the harness currently masks that failure with `|| true`. No pass/fail delta or application scoreboard is claimed until the suite checkout is repaired or pinned to a vendor-consistent revision.
