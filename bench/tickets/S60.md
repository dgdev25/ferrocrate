# S60 — the CRI server and the CLI use different state directories, and rootless cannot start
- component: ferro-cri · class: product · status: resolved · first seen: 2026-08-27
- command: `FERROCRATE_HOME=<dir> ferro-cri` as a normal user
- Ferrocrate: exits with `Runtime(Io(Os { code: 13, kind: PermissionDenied }))`.
- cause: `ferro-cri/src/server.rs` reads `FERROCRATE_RUNTIME_DIR` and falls back to `/var/lib/ferrocrate`, which a normal user cannot create or write. The CLI and the daemon read `FERROCRATE_HOME` and fall back to `~/.ferrocrate`. The two binaries therefore disagree about where state lives.
- consequences, both real: rootless `ferro-cri` cannot start at all without an override nothing documents; and when it is given one, a container created through CRI is invisible to `ferro-cli` and the reverse, because they are reading different stores.
- fix: read the same variable with the same precedence in both, and use the same rootless-aware default. Keep `FERROCRATE_RUNTIME_DIR` working as an alias if anything depends on it.
- test: with only `FERROCRATE_HOME` set, start `ferro-cri`, create a sandbox through CRI, and assert `ferro-cli containers --all` lists it.
- found by: unblocking the critest suite, which had never run because no `ferro-cri` binary had been built.
- resolution: `14703282` makes `FERROCRATE_HOME` authoritative for CRI as it is for the CLI, retains `FERROCRATE_RUNTIME_DIR` as a lower-precedence alias, and falls back to `~/.ferrocrate`. Unit proof covers precedence and alias resolution.
