# S166 — run: `stop`, `exec` and `start` don't respect Docker's paused-container contract

- apps: all · step: stop, exec, start · class: product · status: open · first seen: 2026-08-28
- command: `run -d --name fz-<tag> alpine:3.20 sleep 300`, `pause fz-<tag>`, then `stop --timeout 1 fz-<tag>` / `exec fz-<tag> true` / `start fz-<tag>`
- Docker: `stop` on a paused container exits 0 and ends in `exited` (Docker unpauses internally as part of stopping). `exec` on a paused container refuses with exit 1, "unpause the container before exec". `start` on a paused container refuses with exit 1, "cannot start a paused container" (start is for stopped containers, not paused ones).
- Ferrocrate: `stop --timeout 1` exits 1 with a lifecycle conflict (`expected_status=running current_status=paused`) instead of succeeding. `exec` runs successfully in a paused container instead of refusing. `start` exits 0 on a paused container instead of refusing.
- cause: the container lifecycle state machine treats `paused` as outside the states `stop`/`exec`/`start` know how to handle, rather than giving each verb an explicit paused-state rule matching Docker's.
- scope: any script or tool that pauses a container as part of a lifecycle sequence and then stops, execs into, or starts it.
- test: pause a running container, then assert `stop` succeeds and ends `exited`; assert `exec` refuses with an "unpause first" message; assert `start` refuses with a "cannot start a paused container" message.
- evidence: found by the 200-sequence differential fuzzer during the S40-S53 acceptance run, 2026-08-28, verified against Docker directly.
