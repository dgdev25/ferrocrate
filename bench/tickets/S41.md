# S41 — run: container state is reported as `killed` or `stopped` after termination
- apps: all · step: kill, stop · class: product · status: closed (202d84ca) · first seen: 2026-08-27
- command: `kill <name>` on a running container, then `ps -a` (minimal sequence: `run -d --name fz-<tag> alpine:3.20 sleep 300`, `kill fz-<tag>`, `ps -a`); same with `stop --timeout 1`
- Docker: the container's State is `exited` after both `kill` and `stop`. Docker's state vocabulary is created, running, paused, restarting, removing, exited, dead — kill and stop are ways to reach `exited`, not states of their own.
- Ferrocrate: the container's status is `killed` after a kill and `stopped` after a stop. Anything that parses `docker ps` output for `exited` (compose, restart loops, the bench suites' wait-for-exit helpers) never matches.
- cause: the container status model stores the termination cause as the status instead of a terminal state.
- scope: both the signal path (`kill`) and the graceful path (`stop`).
- test: run detached, `kill`, then assert `ps -a` reports `exited`; repeat with `stop --timeout 1`. Both text and `--format json`.
- seed: `bench/fuzz/seeds/20260827-kill-6d78b0a1.json`, `bench/fuzz/seeds/20260827-stop-*.json`
- note: the fuzzer maps `killed` and `stopped` to `exited` when comparing state so sequences continue past them; the mapping is in `bench/fuzz/fuzz.py` (`FerroEngine.STATUS_MAP`) and must be removed when this is fixed.
