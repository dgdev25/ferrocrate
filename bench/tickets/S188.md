# S188 — run: `stop` then `start` on the same container fails to rebind its own port

- apps: any app whose process binds a fixed port from an env var (found via battleships, a real external repo, not the bench matrix) · step: stop, start · class: product · status: open · first seen: 2026-08-28
- command: `run -d --name X -p <host>:3000 <image>` (image's process listens on `:::3000` internally), then `stop X`, then `start X`.
- Docker: `stop` fully releases the container's network state; `start` relaunches the same process, which binds port 3000 again without conflict.
- Ferrocrate: `start` after `stop` on the same container fails. The workload's own stderr shows `Error: listen EADDRINUSE: address already in use :::3000` from inside the container process itself (not a host-level port conflict — verified separately that an unrelated real Docker container's host-level use of literal port 3000 was a red herring, not the cause). The daemon's reconcile loop then logs `had stale running pid <pid>, marking exited` a few seconds later, and the container ends up `exited` again despite `start` returning success with no error.
- cause: not yet isolated. `stop_authorized` (ferro-core/src/runtime.rs) does properly wait for both the workload and launcher PIDs to stop existing before returning (verified in `stop_pid_verified`, ferro-core/src/process_lifecycle.rs) — the OS-level process is confirmed dead. The container uses `network_backend=ebpf`, which per the runtime's own field names (`self.ebpf_network: Option<EbpfNetwork>`, `self.shared_network_created`) is a network object shared at the runtime level rather than recreated per-container. The most likely cause is that this shared network setup (or something it retains, e.g. a proxy/relay socket for the container's declared port) is not torn down or reset between the container's own stop and its own restart, leaving something still bound to the container-internal port even though the workload process itself is gone. This needs netns/socket-level investigation (e.g. `nsenter` into the container's actual network context at the moment of the second bind, not host-level `ss`) to confirm.
- scope: any `docker stop && docker start` cycle on a container whose process binds a fixed, non-ephemeral port — a very common pattern (most web app images hardcode or default to one port). This is a basic, frequently-used daily-driver workflow.
- test: build a minimal image whose process binds a fixed port and logs its own bind errors; `run -d`, confirm serving, `stop`, `start`, confirm serving again on the same port without an internal EADDRINUSE.
- evidence: found 2026-08-28 during the first real-world pilot test (battleships, `/data/dev/battleships`, a plain external Dockerfile, not part of the bench matrix), reproduced 3 times in a row on both a reused container name and a fresh one.
