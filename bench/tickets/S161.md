# S161 — BuildKit Dockerfile platform and OS-version arguments are not evaluated as BuildKit expressions
- suite: buildkit-dockerfile (at least 16 direct product failures) · class: product · status: open · first seen: 2026-08-28
- command: `GO_TEST_TIMEOUT=0 SUITE_SRC=/data/dev/bench-suites bash bench/suites/run-suite.sh buildkit-dockerfile --engine ferrocrate`.
- Docker: `FROM --platform` and implicit platform arguments are expanded and validated as BuildKit expressions, including an accurate error for undeclared/misspelled variables; multi-platform metadata paths remain representable even when a particular runtime cannot execute every platform. Ferrocrate instead rejects the raw expression as an unsupported instruction, tries to pull malformed names such as `library/base-`, or returns only `linux/amd64 is available` before the expected expression validation.
- cause: platform flags and BuildKit automatic arguments are handled by the local image builder as already-resolved runtime values rather than by a Dockerfile/frontend expression phase; OS-version and multi-platform exporter paths inherit the same gap.
- scope: `FROM --platform`, `BUILDPLATFORM`/`TARGETPLATFORM` and related automatic args, OS-version arguments, and multi-platform OCI/provenance exports.
- test: solve a Dockerfile that uses valid automatic platform args and one that misspells an arg; assert the valid expansion and Docker-compatible invalid-expression diagnostic before platform execution is selected.
- evidence: `TestPlatformArgs*`, `TestPlatformWithOSVersion`, `TestMaintainBaseOSVersion`, `TestMultiNilRefsOCIExporter`, `TestDuplicatePlatformProvenance`, and `TestUndeclaredArg` failures in the fresh run.

Status note: open — reproduced against Docker 29.7.2: automatic platform
expressions expand and an undeclared expression fails before image resolution.
The Ferrocrate bridge still delegates one host platform to the classic builder,
so `TARGETOSVERSION` and multi-platform OCI/provenance exporter metadata are
not representable. The focused BuildKit-suite reproduction also hit the local
dockerd-forwarder accept-loop crash before those integration cases could run
to a product verdict.
