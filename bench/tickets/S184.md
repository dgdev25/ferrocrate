# S184 — run: `stop` leaves the container workload listening, so `start` cannot restart it
- apps: actix-basics, battleships, docker-todo, flask-tutorial, gin-basic, mdn-static, node-getting-started (with downstream Compose/port effects) · steps: start, health, kill and dependent lifecycle probes · class: product · status: closed · first seen: 2026-08-28
- command: `run -d --name fz-<tag> -p 34911:8080 bench/actix-basics:latest`, wait for `curl -sf http://127.0.0.1:34911/`, then `stop fz-<tag>`, `start fz-<tag>`, and repeat the curl.
- Docker: `stop` terminates the listening workload; `start` restores it and the second HTTP probe succeeds.
- Ferrocrate: the initial HTTP probe succeeds and `start` prints the container name, but the restarted service never binds. Its logs contain `Error: Os { code: 98, kind: AddrInUse, message: "Address already in use" }`; the second probe returns HTTP 000. The subsequent `kill` correctly rejects the now-exited wrapper, which is downstream of the failed restart.
- cause: the stop/restart lifecycle does not fully reap the workload process tree or its network namespace listener before launching the replacement workload. This is distinct from S10 (host slirp forwarder reaping after remove) and S22 (orphan cleanup after the store record disappears): the record remains present and the stale listener prevents its own restart.
- scope: stopped web containers and any Compose/lifecycle sequence that reuses a service port. The fresh matrix’s `start`/health failures are the direct form; later `top`, `exec`, `cp`, `pause`, and `kill` failures can be cascading consequences of the exited replacement.
- test: start a port-published HTTP container, prove it serves, stop it, prove its workload/listener is gone, start it, and prove it serves again. Assert no prior workload PID or listener remains after stop and that the restarted container reports `running`.
- proof: the isolated 2026-08-28 matrix at head `e7145b7d` records Ferrocrate-only `start` failures after successful initial lifecycle steps. Manual reproduction with `FERROCRATE_HOME=/path/to/ferrocrate-lab/runtimes/app-bench-refresh3` and `FERROCRATE_BIN=/data/dev/ferrocrate-app-bench-refresh3/target/release/ferro-cli` served Actix before stop, then reproduced the bind error and HTTP 000 after start. Earlier committed app records show the same app/step failures rather than a passing baseline, so this is not asserted as a regression of S40.
- fix: S192's verified rootless process-group shutdown reaps listening descendants; the published-listener stop/start regression passes.
