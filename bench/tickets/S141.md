# S141 — BuildKit Dockerfile errors omit source definitions and ranges
- suite: buildkit-dockerfile (28 direct product failures) · class: product · status: closed (b49f4792) · first seen: 2026-08-27
- command: `SUITE_SRC=/data/dev/bench-suites bash bench/suites/run-suite.sh buildkit-dockerfile --engine ferrocrate` (notably `TestErrorsSourceMap/*` across dockerd, dockerd-containerd, and builtin/client frontends)
- Docker: an invalid Dockerfile solve returns an error whose `errdefs.Sources(err)` contains one `Dockerfile` source, its original bytes, a definition, and ranges for the offending line or lines. Ferrocrate: the solve fails as expected, but `errdefs.Sources(err)` is empty, so the test's expected source count is 1 and actual count is 0.
- cause: the BuildKit control/frontend error conversion serializes only the failure message and drops the structured source metadata required by BuildKit's error-definition protocol. This is independent of S70 (gateway `Inputs`) and S71 (shell-form parsing): these cases intentionally use invalid Dockerfiles and fail at the expected semantic boundary, but without diagnostic provenance.
- scope: every frontend-originated Dockerfile parse/validation error exposed over BuildKit control, including multiline and flag errors; clients cannot map an error back to a Dockerfile location.
- test: perform a BuildKit client solve for an invalid multiline Dockerfile, assert failure, then assert `errdefs.Sources(err)` has one `Dockerfile` entry with the input bytes, non-nil definition, and ranges containing each invalid line.

## Fix
The BuildKit error conversion now projects structured source metadata — the `Dockerfile` source, its original bytes, a definition, and offending line ranges — instead of serializing only the failure message.
