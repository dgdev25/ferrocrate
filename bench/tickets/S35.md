# S35 — daemon: compat tag endpoint answers "not found" for every reference form; images stored under registry-1.docker.io are invisible to docker.io lookups
- suite: moby-integration (blocks the entire ferrocrate leg: TestMain cannot seed its frozen fixtures, so every integration package panics and the run records 3 tests) · class: product · status: resolved · first seen: 2026-08-27
- command: `POST /images/{name}/tag` through the Docker-compat API, and every client lookup that normalizes `busybox:latest` to `docker.io/library/busybox:latest`.
- Docker: tags the image and answers 201; `docker.io/library/busybox` and `registry-1.docker.io/library/busybox` are the same repository.
- Ferrocrate: `Error response from daemon: not found` for all forms observed: source ref by tag (`busybox:latest`), source ref by digest (`hello-world@sha256:d58e…`), raw API with unencoded path (`POST /images/hello-world@sha256:…/tag` → 404). Meanwhile `GET /images/json` lists the pulled images under `registry-1.docker.io/library/…`, and the store keeps digest-pulled entries across daemon restarts, so the data is there — the tag/lookup path cannot reach it. One transient success was observed for a digest ref minutes after a same-session tag-pull of the same image, but it does not reproduce on a fresh daemon.
- cause: two defects acting together: (1) the tag endpoint resolves the source reference against a name index that does not contain registry-1.docker.io-prefixed entries (docker clients canonicalize to docker.io, which never matches); (2) tag-by-digest fails even when the digest is present in the store.
- scope: reference normalization between docker.io and registry-1.docker.io in the compat server, plus lookup-by-digest in the tag handler. Blocks every workflow that retags an image through the Docker API (CI tags, docker tag, compose fixture pinning).
- test: on a fresh daemon: pull `busybox` (raw API `POST /v1.43/images/create?fromImage=busybox&tag=latest`), then `POST /v1.43/images/busybox:latest/tag?repo=busybox&tag=frozen` must answer 201 and `GET /v1.43/images/busybox:frozen/json` must answer 200; same for a digest source ref.
- note: this is why the moby-integration ferrocrate leg is recorded as blocked instead of producing numbers: the frozen-image pre-seed (busybox:latest/glibc, debian:trixie-slim, hello-world:frozen/latest/amd64/arm64) cannot be tagged, TestMain's imageExists() misses, its own pull hits S32, and the package panics.
- resolution: the Docker-compat handler percent-decodes the source path and delegates lookup to the canonical image-tagging resolver, which normalizes Docker Hub to `registry-1.docker.io` and resolves `name@digest` through the digest index. `docker_compat_tag_resolves_docker_hub_aliases_and_digest_sources` proves both forms against a fresh socket daemon; it passed on 2026-08-27. The original observation was made with a stale release artifact.
