# S37 — ferro-cri: CRI v1 image API answers with invalid gRPC wire-format data, so critest cannot connect
- suite: critest (all 137 failures behind it; 0 real specs pass) · class: product · status: reopened · first seen: 2026-08-27
- command: `critest --runtime-endpoint unix:///run/user/1000/ferrocrate-cri.sock` against `target/release/ferro-cri` (bench/suites/run-suite.sh critest)
- Docker/CRI contract: the runtime endpoint answers the CRI v1 `ImageService` (`runtime.v1.ImageService/ListImages` etc.) with valid protobuf over gRPC; every conformant CRI client can validate the connection.
- Ferrocrate: critest's connection validation (`validate service connection: validate CRI v1 image API`) fails on every spec with `rpc error: code = Internal desc = grpc: failed to unmarshal the received message: proto: cannot parse invalid wire-format data`. Recorded 2026-08-27T11:49Z; every BeforeEach (framework.go:59) fails with the same message, so the suite runs 142 specs, records 0 passes and 137 fails plus 5 skipped benchmarks. The one recorded "pass" is the empty-named BeforeSuite node.
- cause: the ferro-cri gRPC image service emits a response the Go gRPC client cannot parse as protobuf: either the message is serialized wrong, or the HTTP/2 framing/message-length prefix on the stream is malformed. The error is raised client-side while unmarshalling the reply to the validation RPC, before any test logic runs.
- scope: the CRI v1 image service handlers in ferro-cri and/or the gRPC codec path (message framing, length prefix, compression flag). Until this is fixed no critest spec can run, so the whole CRI conformance surface is unverified.
- test: start ferro-cri, then `critest --runtime-endpoint <sock> --ginkgo.focus 'image list'` must connect and report the spec result rather than failing connection validation; a plain gRPC `ListImages` call against the socket must return a parseable `ListImagesResponse`.
- blocked-by note: bench/suites records this leg as blocked on S37; rerun after the fix. No Docker oracle exists for critest by design (Docker exposes no CRI endpoint).
- resolution: `ferro-cri` serves the generated CRI v1 tonic service directly; the external process socket now has a regression test, `cri_process_image_service_list_images_is_valid_protobuf`, which starts the binary and decodes `ListImagesResponse` with the generated client. It passed on 2026-08-27, so this does not need a separate chain. The recorded invalid wire format came from a stale release artifact.


## Reopened
Reopened 2026-08-27, coordinator. The "stale release artifact" diagnosis was wrong. Rebuilt `ferro-cri` fresh (after S60/S61/S62 merged) into an isolated runtime with the correct FERROCRATE_CRI_SOCKET, and critest reproduces the identical symptom: `rpc error: code = Internal desc = grpc: failed to unmarshal the received message: proto: cannot parse invalid wire-format data` on every one of 137 specs, 0 passed.

The regression test `cri_process_image_service_list_images_is_valid_protobuf` passing is not evidence the wire format is correct: it uses a Rust tonic client against the tonic server, the same stack on both ends. critest uses a real Go gRPC client. An HTTP/2 framing, content-type, or trailer issue that a same-stack Rust client tolerates or never exercises can still be invisible to that test while breaking every real-world consumer (Go clients, Kubernetes itself, since CRI's actual purpose is being called by kubelet, which is Go).

Next step: reproduce with a Go gRPC client directly (grpcurl, or a two-line Go program) against a freshly started ferro-cri, to localize whether the defect is in message framing, the length-prefix, or a served content-type that only a strict Go client's h2 stack rejects. Do not close this again on a same-stack test alone.
