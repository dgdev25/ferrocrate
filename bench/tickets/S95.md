# S95 — Expose an OCI Runtime Specification command-line runtime entrypoint

- suite: oci-runtime · class: coverage gap · status: scoped — requires a dedicated OCI adapter · first seen: 2026-08-27
- command: `OCI_RUNTIME=<runtime> SUITE_SRC=/data/dev/bench-suites bash bench/suites/run-suite.sh oci-runtime --engine <engine>`
- required contract: the path in `OCI_RUNTIME` must be a direct OCI Runtime Specification implementation that consumes an OCI bundle (`config.json` plus rootfs) and supports the lifecycle commands `create`, `start`, `state`, and `delete` for a container ID.
- Ferrocrate evidence: a fresh `cargo build --release -p ferro-cli` produced `target/release/ferro-cli`. Its `create` command requires an image reference and its `start` command accepts existing Ferrocrate container names; `ferro-cli state` and `ferro-cli delete` both exit 2 with `unrecognized subcommand`. The CLI help has no OCI-bundle runtime command or separate runtime binary.
- missing: a documented executable entrypoint (for example `ferro-runtime`) implementing the OCI Runtime Specification lifecycle directly, including bundle parsing, per-runtime state storage, `state` JSON output, and idempotent `delete`. Docker-compatible daemon/API operations are not a substitute because runtime-tools invokes the executable directly.
- impact: no Ferrocrate result can be produced for the `oci-runtime` suite, so a Docker/runc versus Ferrocrate scoreboard comparison would be invalid rather than a product measurement.
- acceptance: a release-built Ferrocrate binary can be assigned to `OCI_RUNTIME`; the runtime-tools validators invoke its `create`, `start`, `state`, and `delete` commands against generated bundles; `bench/suite-scoreboard.py` receives genuine `oci-runtime-docker` and `oci-runtime-ferrocrate` result files.

## Oracle evidence

With the isolated `FERROCRATE_HOME=/path/to/ferrocrate-lab/runtimes/ocitools` and `XDG_RUNTIME_DIR=/path/to/ferrocrate-lab/runtimes/ocitools/run`, `/usr/bin/runc` ran all 58 discovered validators: 36 passed and 22 failed. The remaining failures are host/runtime validation limitations recorded in `bench/results/2026-08-27/suite-oci-runtime-docker.jsonl`, not a Ferrocrate comparison.

## 2026-08-27 scope decision

A thin `ferro-runtime create|start|state|delete` wrapper is not feasible without
substantial new runtime work; it would only reproduce command names, not the OCI
Runtime Specification contract exercised by runtime-tools.

- `ContainerRuntime::run_with_store_with_id` is image-store-backed and launches
  immediately. It resolves an image, materializes its layers into
  `$FERROCRATE_HOME/containers/<id>/rootfs`, and creates the process in the same
  operation. There is no create-only API that adopts the bundle's `root.path`,
  persists its process configuration, and defers process launch to `start`.
- `__ferrocrate_rootfs_launch` is a private post-spawn helper used only by
  `ferro-cli` and `ferro-cri`. It accepts already-normalized launcher arguments,
  then chroots and execs; it neither reads OCI `config.json` nor implements
  namespaces, mounts, hooks, cgroups, seccomp, rlimits, uid/gid mappings, or
  durable OCI state.
- The runtime-tools suite directly invokes `create --bundle <path> <id>`, then
  separately invokes `start`, `state`, `kill`, and `delete` (including `--force`).
  Its 58 validators exercise state JSON, pidfiles, lifecycle ordering and hooks,
  process credentials/capabilities/rlimits, rootfs and mount flags, Linux
  namespaces, cgroups, sysctls, devices, seccomp, and cleanup. Ferrocrate has no
  OCI spec model/dependency or adapter translating those settings into its
  image-centric runtime model.

Required follow-on work is a separately scoped OCI runtime adapter: an OCI
`config.json` model and validation layer; bundle-rootfs ownership/adoption;
durable OCI state and pidfile support; explicit create/start/delete state
transitions; hook execution; and a complete, fail-closed mapping (or documented
rejection) for the Linux process, namespace, mount, cgroup, device, seccomp, and
resource fields. Only after that adapter exists can `ferro-runtime` be exposed
and an `oci-runtime-ferrocrate` result be compared with the runc oracle.

No Ferrocrate OCI suite result or scoreboard comparison is recorded: doing so
without the direct OCI entrypoint would be invalid. No runtime workload was
launched during this scope investigation, so the S95 isolated runtime owns zero
`bwrap` and `slirp4netns` processes.
