# S159 — BuildKit Dockerfile security and network entitlements are not enforced with Docker semantics
- suite: buildkit-dockerfile (22 direct product failures) · class: product · status: partial · first seen: 2026-08-28
- command: `GO_TEST_TIMEOUT=0 SUITE_SRC=/data/dev/bench-suites bash bench/suites/run-suite.sh buildkit-dockerfile --engine ferrocrate`.
- Docker: a denied `security.insecure` or `network.host` entitlement is rejected before executing the Dockerfile step; when granted, the corresponding sandbox/network behavior is applied. Ferrocrate executes or misparses the step instead, producing capability-command failures such as a failed `CapBnd` shell assertion or `--security=sandbox` reaching `/bin/sh`; other client variants return the S70-style unimplemented callback error.
- cause: the BuildKit solve path does not propagate/validate the frontend entitlement set before lowering `RUN` options into the local builder, so denied and granted modes do not form Docker's required semantic boundary.
- scope: `RUN --security=insecure`, `RUN --security=sandbox`, insecure-device whitelist cases, and `RUN --network=host` / network entitlement cases.
- test: for each security and network entitlement, assert a denied request returns the canonical entitlement error before execution and a granted request reaches an appropriately configured execution path.
- evidence: fresh `TestRunSecurityDefault`, `TestRunSecurityInsecure`, `TestRunSecuritySandbox`, `TestInsecureDevicesWhitelist`, and `TestRunGlobalNetwork` failures.

Partial 2026-08-30: verified the upstream semantics and the ticket's
reproducer. `security.insecure` and `network.host` are checked against the
outer solve's entitlement list before an individual Exec is run;
`--security=sandbox` is a no-op/default. Ferrocrate's outer protobuf includes
the entitlement field, but its gateway delegates the whole Dockerfile to the
classic builder, which has no per-`RUN` security mode, network mode, or device
whitelist execution interface. A preflight-only allow-list would still claim a
granted `--security=insecure`/`--network=host` execution without supplying its
Docker semantics. Remaining work is parser lowering into per-step runtime
options plus daemon-side entitlement configuration and device whitelist
enforcement.

Partial 2026-08-30 (chain/s158-159): implemented the verifiable execution
surface from the pinned upstream fixtures. `RUN --security=sandbox|insecure`
is now parsed as instruction metadata and participates in the cache identity;
sandbox uses Docker's 14-capability default mask plus `no_new_privs` and the
existing seccomp policy, while insecure retains capabilities, omits those
restrictions, and exposes the fixed automatic-device set when present. The
existing per-`RUN` network lowering now shares the same two-sided entitlement
gate. Outer solves must request `security.insecure` or `network.host`, and the
daemon must separately permit each with repeatable
`--allow-insecure-entitlement`; denials use BuildKit's canonical error before
the Dockerfile executes. The minimal regressions cover security flag lowering,
the exact sandbox/insecure mode selection, and granted/denied daemon checks for
both entitlement names.

This does not close S159. A fresh pinned-suite run after the execution changes
reached 383 pass, 42 fail, and 17 skip, but its dockerd shim terminated in
`accept()` for the remaining security cases. More importantly, that adapter
proxies every matrix worker to one prestarted Ferrocrate daemon and does not
forward each worker's daemon entitlement configuration, so it cannot verify
both the granted and denied variants of the new daemon gate. Rootful automatic
device creation and the upstream loop-device whitelist also remain
unimplemented. Those cases need a configuration-aware adapter (or equivalent
direct daemon fixtures) and rootful device coverage before S159 can be marked
closed.
