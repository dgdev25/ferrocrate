# S22 — containers outlive their store records after a harness run
- source: host audit during a coordination handover · class: product · status: open · first seen: 2026-08-26
- observed: nearly two hours after the docker-client conformance harness finished, its containers were still running — `bwrap --bind /tmp/ferrocrate-s14-final-root.*/containers/<id>/rootfs` and their `httpd -f -p 18091/18092` payloads — while `ferro-cli containers --all` reported `no entries`. A second pair of `bwrap --unshare-all` processes had been alive for roughly sixteen hours.
- why it matters: the process outlives the record, so nothing can find or clean it. `containers`, `rm` and `system prune` cannot help because the store believes there is nothing there. It held CPU and a published port, and it was discovered only because another project audited the host before taking a shared window.
- relation to S10: same family — a runtime resource surviving the thing that owns it. S10 fixed the network helper leak and is verified; this is the container process itself, and it survives the harness's own cleanup and the temporary root directory being removed.
- repro: run `scripts/docker-client-conformance.sh` to completion, then `ps -eo args | grep bwrap` — the fixture's containers are still there.
- fix: tie each container's process tree to its store record and reap on daemon start and on harness teardown; a container whose rootfs or record is gone must be killed, not orphaned. Add the process-count check to the fuzzer's cleanup audit (bench/fuzz/fuzz.py --audit already counts helpers; add bwrap and container payloads).
