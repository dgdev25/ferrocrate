# S162 — Dockerfile RUN mount/resource options are not applied by the BuildKit execution bridge
- suite: buildkit-dockerfile (at least 18 direct product failures) · class: product · status: closed 2026-08-30 · first seen: 2026-08-28
- command: `GO_TEST_TIMEOUT=0 SUITE_SRC=/data/dev/bench-suites bash bench/suites/run-suite.sh buildkit-dockerfile --engine ferrocrate`.
- Docker: BuildKit applies supported `RUN --mount` ownership/tmpfs/cache settings and sandbox resource settings, and rejects misspelled mount flags at parse time. Ferrocrate reports cache-owner EPERM, rejects valid tmpfs-size syntax, sends `--security=sandbox`/unknown `--mont` through to the shell, cannot provide `/dev/shm`/cgroup expectations, or fails to create cache/mount output paths.
- cause: Dockerfile RUN options are only partially parsed and are not translated into the rootless BuildKit execution environment; validation and execution therefore diverge together from Docker's mount/resource contract.
- scope: cache mount uid/gid, tmpfs size, duplicate/meta mounts, shared memory size, cgroup parent/resources, ulimit, and invalid RUN mount flag diagnostics.
- test: run focused Dockerfiles for a valid cache uid/gid mount, valid tmpfs size, invalid `--mont`, and `/dev/shm` size; assert the expected mount state or early Docker-compatible validation error.
- evidence: fresh `TestCacheMountUser`, `TestMountTmpfsSize`, `TestMountDuplicate`, `TestMountMetaArg`, `TestMountInvalid`, `TestShmSize`, `TestCgroupParent`, `TestLinuxResources`, and `TestUlimit` failures.

Status note: closed — verified against Docker 29.7.2 and BuildKit's Dockerfile
frontend/LLB resource contract. The Dockerfile frontend bridge now parses and
passes `shm-size`, `ulimit`, `cgroup-parent`, memory/memswap, CPU
quota/period/shares/cpuset, and pids-limit into the classic executor with the
same signedness, zero/infinity behavior, accepted cpuset whitespace and bounds,
CSV ulimit quoting, and absolute cgroupfs-parent spelling as Docker. It also
rejects every unsupported leading RUN option and mount key/type before shell
execution, including Docker's edit-distance suggestions and exact
network/security diagnostics. Earlier S162 commits cover cache uid/gid, tmpfs
`size=`, duplicate/meta mounts, cache filtering, secret/SSH metadata, and
global/per-RUN network selection.

Regression evidence is the focused `buildkit_frontend_*` resource tests,
`build_cgroup_parent_accepts_docker_absolute_cgroupfs_path`, and the RUN mount
diagnostic matrix; the complete workspace and Docker-client conformance gates
pass in BuildKit-default and classic modes. The local dockerd shim's accept-loop
traceback was reproduced and fixed with a SIGINT regression. A focused upstream
BuildKit rerun now reaches Ferrocrate, but its S162 cases stop earlier in the
separate S156 session/filesync boundary (`inactive stream` or `Is a directory`),
so that run is not claimed as execution evidence for these bridge attributes.

Out of scope and still open elsewhere: session-provided secret/SSH import and
SSH socket ownership proxying; subordinate-ID ownership mapping; delegated
rootless cgroups and enforceable rootless tmpfs sizing; managed outbound
sandbox networking; cache `from`/`source` and readonly cache mounts; and direct
client LLB vertex execution. None of those paths drops Dockerfile frontend
resource attributes before the classic executor, which is the S162 boundary.
