# S70 — BuildKit gateway solve returns `method not implemented`
- suite: buildkit-dockerfile (20 failures behind it) · class: product · status: fixed · first seen: 2026-08-27
- command: `SUITE_SRC=/data/dev/bench-suites bash bench/suites/run-suite.sh buildkit-dockerfile --engine ferrocrate`
- Docker: BuildKit Dockerfile frontend solves complete for the corresponding `frontend=client` workers. Ferrocrate: the client receives `Internal: buildkit solve: method not implemented`.
- cause: the transport dispatched `Ping`, `Solve`, and `Return`, but a real `frontend=client` Dockerfile frontend calls `LLBBridge/Inputs` before `Return`. That unimplemented RPC caused the frontend to return gRPC code 12, which the outer solve surfaced as `Internal: buildkit solve: method not implemented`.
- scope: 20 distinct non-interruption failures: source-date-epoch exporters plus the `frontend=client` variants of the security/insecure-device tests.
- test: extend the existing BuildKit control integration pattern to perform a gateway Dockerfile solve through the BuildKit client and assert a successful result rather than gRPC `Unimplemented`.

## Fix

- Added the generated BuildKit gateway `InputsRequest`/`InputsResponse` messages and dispatched `LLBBridge/Inputs`.
- The Inputs handler locates the matching outer solve, runs its Dockerfile through the existing session/local and classic-builder path, records the image result, and returns a successful empty inputs map. The subsequent frontend `Return` completes the outer result exchange.
- Regression coverage: `buildkit_control_dispatches_gateway_callback_methods` now asserts the real client callback route, including `Inputs`.
