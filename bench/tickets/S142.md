# S142 — BuildKit Dockerfile frontend does not deliver lint warnings through result or progress APIs
- suite: buildkit-dockerfile (500 product failures in `checkLinterWarnings` progress/unmarshal variants) · class: product · status: closed (2e2437a0) · first seen: 2026-08-27
- command: `SUITE_SRC=/data/dev/bench-suites bash bench/suites/run-suite.sh buildkit-dockerfile --engine ferrocrate` (for example `TestAllTargetUnmarshal`, `TestConsistentInstructionCasing`, `TestCopyIgnoredFiles`, and related `warntype=progress`/`warntype=unmarshal` cases)
- Docker: Dockerfile checks deliver expected lint diagnostics both as streamed `client.VertexWarning` values and in the gateway result unmarshalled by the client. Ferrocrate: the check-linter assertions fail; retained stderr tails point to `checkLinterWarnings` and its warning-count assertions rather than a Dockerfile semantic error, and the expected warning result is absent.
- cause: the embedded BuildKit Dockerfile frontend/control path does not preserve BuildKit lint diagnostics in the solve-status stream and gateway result metadata. The direct error-source-map gap is separately tracked by S141; this ticket covers successful/check-mode lint diagnostics rather than failure provenance.
- scope: all Dockerfile linter rules and both BuildKit client delivery forms (`SolveStatus.Warnings` progress and unmarshalled gateway lint results). These diagnostics are part of BuildKit client compatibility even when no image build failure occurs.
- test: invoke a Dockerfile check that deliberately triggers one stable rule (for example `FromAsCasing`) through the Ferrocrate BuildKit client; assert the matching rule, detail, location, and URL arrive once in the progress stream and once in the unmarshalled result.

## Fix
The BuildKit gateway `ReadFile` callback now treats the client frontend's
context-root `.dockerignore` probe as an absent optional file. Previously only
the Dockerfile-specific sibling name was accepted, so the client frontend
failed before it could return `result.json` lint metadata or send `Warn`
callbacks. The existing lint result/progress projections can now reach the
BuildKit client APIs.
