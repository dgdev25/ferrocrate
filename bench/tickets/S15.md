# S15 — build: multi-stage Dockerfiles do not resolve stage names or provide stage tools
- source: real-app bench · apps: actix-basics, gin-basic, spring-petclinic, docker-todo · step: build · class: product · status: open · first seen: 2026-08-26
- Docker: all four build. Ferrocrate fails in two related ways:
  - `FROM x AS base` then `FROM base` → `invalid Dockerfile: base image not found: base` (docker-todo). A stage name is being resolved as a registry reference instead of an earlier stage.
  - the build stage's own tooling is missing: `RUN cargo build …` → `/bin/sh: 1: cargo: not found` (exit 127) on `FROM rust:… AS build`; likewise `go` (gin-basic) and `./mvnw` (spring-petclinic).
- reading: the RUN steps appear to execute against the wrong stage's filesystem — the final/runtime image rather than the build stage — which explains both the missing toolchains and the unresolved stage name.
- impact: the single largest cause in the first parity run. Multi-stage builds are the normal shape for Go, Rust and Java projects; three of fourteen bench apps are blocked at step one, cascading to 36 failures each.
- repro: `cd /data/dev/bench-apps/gin-basic && ferro-cli build -t x .` with the bench-generated Dockerfile (`FROM golang:1.25 AS build` … `FROM gcr.io/distroless/static-debian12`).
- fix: resolve `FROM <stage>` against previously named stages before treating it as a registry reference; run each stage's RUN steps in that stage's filesystem; support `COPY --from=<stage>`. Regression tests: a two-stage build that compiles in stage one and copies the artefact to stage two, and a `FROM x AS base` / `FROM base` chain.
