# S33 — daemon: concurrent API requests fail with "could not acquire lock" instead of queueing
- suite: compose-e2e; cli-e2e follow-up coverage · class: product · status: closed · first seen: 2026-08-27
- command: `go test ./pkg/e2e/... -parallel 4` against the Ferrocrate Docker-compat socket (bench/suites/run-suite.sh compose-e2e --engine ferrocrate)
- Docker: the same suite at the same parallelism passes; the daemon serves concurrent requests.
- Ferrocrate: `Error response from daemon: failed to open container store: IO error: could not acquire lock on "<store>/containers.db/db": Os { code: 11, kind: WouldBlock, message: "Resource temporarily unavailable" }`
- cause: each API request that opens the container store takes a file lock without waiting (flock WouldBlock, EAGAIN). Compose issues one request per service in a project concurrently, so any project with more than one container can trip it. Docker treats the store lock as an internal implementation detail and serialises requests internally.
- scope: the daemon request path, not the CLI. Any client that issues parallel requests (compose, buildkit workers, Kubernetes-style controllers) hits this. A fix must wait for or retry the lock, or serialise store access inside the daemon before returning an error to the client.
- test: start the daemon, issue two concurrent `POST /containers/create` requests (or one `compose up` with two services), assert both succeed.
- note: the bench works around it with `GO_TEST_PARALLEL=1` to keep functional signal; the workaround does not close this ticket.
- resolution: `8a064e99` serializes the daemon's short container-store request transactions while releasing the guard before streaming responses. `docker_api_concurrent_container_lists_queue_on_the_daemon_store` sends fifty simultaneous list requests and all receive 200.

## Fix

`8a064e99` queues each Docker-compat request's short container-store
transaction on the daemon guard. The audit covers the request handler,
pre-start attach/start handoff, detached exec, attach, logs, stats, and wait:
the latter six reuse the daemon-owned runtime connection after response
headers and do not open a second container store. The only independent opens
are daemon startup (`ContainerRuntime` and the pending-name store), plus
native CLI/doctor maintenance paths outside the Docker socket.
