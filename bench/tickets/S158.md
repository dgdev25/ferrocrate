# S158 — BuildKit gateway supports only Dockerfile-v0 callbacks, not client/provenance frontend solves
- suite: buildkit-dockerfile (at least 49 direct product failures; 40 retain `buildkit solve: method not implemented`) · class: product · status: partial · first seen: 2026-08-28
- command: `GO_TEST_TIMEOUT=0 SUITE_SRC=/data/dev/bench-suites bash bench/suites/run-suite.sh buildkit-dockerfile --engine ferrocrate`.
- Docker: BuildKit's gateway permits client frontends and provenance/export flows to issue their normal callback solves and returns the referenced result. Ferrocrate: client cases return `Internal: buildkit solve: method not implemented`; the daemon log additionally records `buildkit gateway: only dockerfile.v0 frontend solves are supported`, while built-in provenance cases fail looking up the generated `buildkit/testwithprovenance` image.
- cause: after the S70 `Inputs` addition, the gateway still treats Dockerfile-v0 as its only supported nested solve and does not materialize/generalize the callback result needed by client/provenance frontends. The result is a broader callback surface gap than the original `Inputs` RPC alone.
- scope: client frontend solves, provenance attestations, local provenance exports, and callback-derived image references; ordinary Dockerfile-v0 solves can proceed independently.
- test: run one `frontend=client` Dockerfile solve that requests a provenance result and assert callback solve completion, a non-nil reference/definition, and a resolvable exported image.
- evidence: `TestProvenanceAttestation`, `TestProvenanceExportLocal*`, `TestClientFrontendProvenance`, and client-heredoc/remote-context variants in the 2026-08-28 full result; daemon evidence is in `/tmp/suite-buildkit-dockerfile.1DdXkt/daemon.log`.

Partial 2026-08-30: verified against the upstream client-frontend reproducer.
It performs an arbitrary HTTP LLB callback, reads that callback reference, then
issues multiple Dockerfile callbacks and returns a multi-platform result with
provenance metadata. Ferrocrate's gateway can only materialize a single
Dockerfile result through the classic builder; it has no LLB evaluator,
reference registry/read interface, multi-reference result model, or attestation
exporter. Accepting this flow would return non-resolvable synthetic refs.
Remaining work is an actual BuildKit-compatible LLB/reference execution layer
and exporter path, not a callback allow-list adjustment.
