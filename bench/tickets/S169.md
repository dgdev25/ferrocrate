# S153 — daemon: Docker-compatible request decoding rejects nullable nested objects
- suite: moby-integration (91 directly recorded Ferrocrate-only failures in the 2026-08-28 full run) · class: product · status: open · first seen: 2026-08-28
- command: create/run/attach/log requests that contain Docker's normal nullable nested configuration objects, including `HostConfig`, networking and health-related request fields.
- Docker: accepts `null` for optional nested objects and applies Docker defaults.
- Ferrocrate: rejects the request before its semantic validation with `invalid JSON: invalid type: null, expected a map at line 1 column …`.
- evidence: `Test64BitIPRange` (all parameter variants), `TestAttach`, `TestContainerList_HealthSummary`, `TestLogs`, `TestContainerBindMountInspect`, and many create/inspect paths fail at this common decode boundary; the refreshed result is `bench/results/2026-08-28/suite-moby-integration-ferrocrate.jsonl`.
- cause: the compatibility request structs deserialize optional Docker object fields as required maps instead of accepting `null` and normalizing it to the absent/default representation.
- scope: any Docker API client that serializes an optional nested object as JSON `null`; this masks later, more-specific API behaviour and validation.
- test: socket compatibility tests for representative container-create, network-create, attach and logs requests with optional nested objects encoded as `null`, asserting acceptance and Docker-equivalent defaults.
