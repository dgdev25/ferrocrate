# S181 — `nginx:alpine` service container exits with code 1 during `up -d --wait`

- suite: compose-e2e · class: product defect · status: closed 2026-08-30 — install subordinate-ID maps at the stopped launcher barrier and inherit the FerroCrate AppArmor profile through bwrap · first seen: 2026-08-28
- command: `docker compose up -d --wait` over the suite's start-stop fixture (two services, both `image: nginx:alpine`) (TestStartAlreadyRunning, TestStopAlreadyStopped, TestStartStopMultipleServices)
- Docker: both containers stay running and `--wait` exits 0.
- Ferrocrate: the second-started `simple` container reaches `Started`, then reports `container ...-simple-1 exited (1)`; `--wait` exits 1. The sibling `another` container of the same image keeps running, so the failure is per-container, not per-image.
- impact: 3 failures directly; `TestUnusedMissingEnvFile` and `TestLocalComposeVolume/access_bind_mount_data` (`service "X" is not running`) are likely the same cause and were not counted.
- regression tests: start two containers of `nginx:alpine` in one project, assert both stay running past `--wait`; check `container logs`/exit code capture for the exited one so the reason is visible.
- diagnosis (2026-08-29, reproduction on this bench host at 681a250e): every `nginx:alpine` container under the rootless launcher exits with `nginx: [emerg] chown("/var/cache/nginx/client_temp", 101) failed` — `container logs` captures the reason. The "per-container, not per-image" reading in the record above does not hold: in an isolated reproduction both project containers exit with the same chown failure; the surviving sibling only appears when the second container dies earlier, at start, with `shared network namespace pid:<leader pid> does not exist` because the leader already exited. Two stacked causes, both required for the fix:
  1. The workload user namespace maps only uid 0 (`uid_map` reads `0 1000 1`, written by the `unshare --user --map-root-user --net` launcher in ferro-core/src/runtime.rs), so uid 101 is unmapped and `chown(…, 101)` returns `EINVAL`. Docker-rootless maps the caller's subordinate range (`0 1000 1` plus `1 100000 65535`); `unshare --user --map-root-user --map-auto` (util-linux ≥ 2.40) produces exactly that shape and `chown 101` then succeeds inside the namespace. `--map-auto` cannot simply be added to the launcher: util-linux forks when it installs the multi-entry map and the parent exits, which breaks the launcher contract that the spawned process stays the workload (every rootless start then fails with `rootless workload exited before creating its network namespace`, measured 2026-08-29). The mapping has to be installed on the stopped launcher instead — for example `newuidmap`/`newgidmap` on the launcher pid before release, alongside the existing authorized `apply_user_namespace_mappings` path in ferro-core/src/rootless.rs.
  2. This host's distro AppArmor profile (`/etc/apparmor.d/bwrap-userns-restrict`) attaches to `/usr/bin/bwrap` and stacks `unpriv_bwrap` onto the workload, which denies `CAP_CHOWN` inside the user namespace (audit: `apparmor="DENIED" operation="capable" profile="unpriv_bwrap" comm="chown" capname="chown"`). With the mapping fixed, `chown(…, 101)` becomes the right target uid but is then denied with `EPERM`, so nginx still exits 1. Root cause of the denial is the profile transition at `/usr/bin/bwrap`, so the remedy is profile/packaging-side — the shipped `packaging/apparmor/usr.local.bin.ferrocrate` profile would need to keep the bwrap helper inside the FerroCrate profile (explicit `ix` rule) the way the design note in docs/design/apparmor-rootless-userns.md assumes — not a runtime-code change.
