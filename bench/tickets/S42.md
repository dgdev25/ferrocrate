# S42 — run: `run --network <missing>` leaves no container behind and exits 1, not 125
- apps: all · step: run-net · class: product · status: open · first seen: 2026-08-27
- command: `run -d --name fz2-<tag> --network fzn-<tag> alpine:3.20 sleep 300` where the network does not exist (minimal sequence: one `run -d` for another container, then this command)
- Docker: exit 125, error from the daemon, and the container `fz2-<tag>` remains in state `created`. Docker creates the container, then fails network setup; the failed container must be removed by the caller.
- Ferrocrate: exit 1, `network: not found fzn-<tag>`, and no container exists afterwards.
- cause: the run path validates the network before creating the container record. That ordering is cleaner than Docker's, but it changes two observables at once: the exit status (125 vs 1) and the leftover container.
- scope: any `run` failure after argument parsing — Docker creates first and reports 125 with a half-built container; scripts rely on `docker rm` cleaning it up. Also the exit code: Docker reserves 125 for daemon errors.
- test: run with a nonexistent network; assert exit 125 and that `ps -a` shows the container in `created`. Remove it and assert success.
